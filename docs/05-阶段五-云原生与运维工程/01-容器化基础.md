# 阶段五 · 小点 1：容器化基础（Docker / Compose）

> 所属：阶段五 云原生与运维工程
> 定位：「不会运维的后端不是好全栈」。企业级开发中，你写的代码最终要跑在 Kubernetes 上，出了问题你要能定位。容器是这条链路的最底层地基——先搞懂「镜像怎么打包才又小又安全」，再谈编排。

## 快速入门

> 本节为「容器速览」：先认识 Docker 是什么、解决什么问题；「多阶段构建、层缓存」留在正文提高部分。

### 本讲关键词与概念速查

| 关键词 | 一句话大白话 | 例子 |
|-|-|-|
| Docker | 把应用和依赖打包成一个「容器」跑 | 一处构建到处运行 |
| 镜像 | 应用的「打包模板」（只读） | `nginx:latest` |
| 容器 | 镜像跑起来的「实例」 | `docker run` |
| Dockerfile | 描述怎么构建镜像的脚本 | `FROM` / `COPY` / `RUN` |
| 镜像分层 | 镜像由多层叠加 | 每层可缓存 |
| 多阶段构建 | 先编译再拷贝产物，镜像更小 | 构建→运行分离 |
| 仓库 | 存镜像的地方 | Docker Hub |
| Compose | 本地一键起多容器 | `docker-compose up` |
| Compose 网络 | 同项目服务的默认私网与 DNS | 容器间用服务名，不用 `localhost` |
| 端口映射 | 把宿主机端口转到容器端口 | `8080:8080` 供宿主机访问，不是容器间通信必需 |
| 命名卷（volume） | Docker 管理的持久化目录 | MySQL 数据，随容器删除仍保留 |
| 绑定挂载（bind mount） | 把宿主机指定路径直接挂进容器 | 本地源码、开发配置；依赖宿主机路径 |
| 层缓存 | 复用未变化的镜像层 | 先复制依赖清单，再复制源码 |
| `.dockerignore` | 排除不应进入构建上下文的文件 | 防止 `.git`、密钥和本地产物进入镜像 |
| 安全基线 | 缩小容器权限和攻击面 | 非 root 运行、最小权限、密钥外置 |

### 本讲在解决什么问题

- **问题**：「在我电脑上能跑」——换台机器就不行了。Docker 把「应用 + 依赖 + 环境」打包成镜像，一处构建、到处一致运行。
- **你需要明确的点**：镜像 = 应用打包模板（只读），容器 = 镜像跑起来的实例。**打包的目标是「又小又安全」**：多阶段构建 + 非 root 运行 + .dockerignore。

### 速览形态示意（非完整可运行工程）

> 示例只展示多阶段构建结构：`./mvnw`、`target/app.jar` 和 `app` 用户都依赖项目与基础镜像的实际配置，Temurin 标签也须按目标架构核对。省略了依赖缓存、用户创建、健康检查和镜像版本锁定，不能直接作为生产 Dockerfile。

```dockerfile
# 多阶段构建: 先在构建镜像编译, 再把产物拷进运行镜像 —— 镜像更小
# 阶段 1: 构建
FROM eclipse-temurin:25-jdk AS build      # 用带 JDK 的镜像做编译
WORKDIR /app
COPY . .
RUN ./mvnw -DskipTests package            # 编译出可运行的 jar

# 阶段 2: 运行(只拷产物, 用 JRE 够)
FROM eclipse-temurin:25-jre               # 运行只需 JRE
WORKDIR /app
COPY --from=build /app/target/app.jar app.jar
USER app                                  # 非 root 运行(安全基线)
ENTRYPOINT ["java", "-jar", "app.jar"]
```

> 代码备注（逐行解释）：
> - `FROM eclipse-temurin:25-jdk AS build`：第一阶段用 JDK 镜像，负责编译（写代码用 JDK）。
> - `RUN ... package`：编译出 `app.jar`。
> - 第二阶段 `FROM eclipse-temurin:25-jre`：运行**只需要 JRE**（省掉编译工具，镜像更小）。
> - `COPY --from=build /app/target/app.jar`：只把编译产物拷过来，不拷源码和依赖。
> - `USER app`：非 root 运行——安全基线，防止容器内提权（正文有安全清单）。
> - 这就是「多阶段构建」：构建和运行分离，最终镜像只装运行需要的，又小又安全。

### 常用约定 / 命名提示

- **构建顺序影响缓存**：先 `COPY package*.json`（依赖清单）再 `COPY 源码`——改代码不击穿依赖层缓存。
- **镜像安全三件事**：非 root 用户运行、`.dockerignore` 排除敏感文件、密钥不 COPY 进镜像（用环境变量/挂载）。
- **镜像名**：用 `eclipse-temurin` 官方组织名（别用 `temurin`），Alpine 变体以 Docker Hub tag 为准。

### 2. 镜像与容器的心智模型

- **镜像（Image）**：打包好的只读制品——类比 npm 包（`tarball`），build 一次到处分发。
- **容器（Container）**：镜像的一个运行实例——类比「`node_modules` 装好后跑起来的进程」，同一个镜像可以起 N 个互不干扰的容器。容器为什么轻量：它**不装操作系统**，多个容器共享宿主机内核，靠**命名空间隔离（Namespace，切视野——像给每个容器一间独立房间，房间里只看得到自己那部分的进程 / 网络 / 文件系统）**切开进程 / 网络 / 文件系统的视野、靠**控制组（cgroup，掐配额——像给房间装水电表，CPU / 内存用超了直接断供）**限住 CPU / 内存——这也是它和虚拟机（每个都带独立内核、由 Hypervisor 虚拟化硬件）的本质区别。

> **生活版——月饼模具与压出来的月饼**：模具负责定型，是「模板」，随便多少人共用、共用也不坏（只读）；月饼是按模具压出来的「实物」，可以吃掉、也可以重新压一块，但模具始终不随月饼改变。换成容器的语言：**镜像 = 模具（只读模板，可共享），容器 = 按模板起的实例（可写、可丢、可重复起）**——同一个镜像起 100 个容器互不干扰，改了某个容器里的文件，镜像原样未动。

```mermaid
flowchart TB
    subgraph VM[虚拟机方式：每台都是一台完整小电脑]
        VM1["VM1<br/>应用 + 自带完整操作系统内核"]

    subgraph CONTAINER[容器方式：共享同一个内核，只切各自的视野]

    CT2 === K
```

- **分层结构（最关键的心智）**：镜像由只读的**文件系统差异层**和镜像配置组成。`RUN`、`COPY`、`ADD` 会形成文件系统差异层；`ENV`、`CMD`、`ENTRYPOINT`、`USER`、`WORKDIR`、`EXPOSE` 等主要写入镜像配置/元数据。构建器仍会按指令及其输入判断缓存，但不能把“每一行 Dockerfile”都理解成一个文件系统层。

```text
镜像层（自下而上，层与层叠加）
┌─────────────────────────────────────┐
│ L4: COPY app.jar（常变）            │ ← 源码一改这层就失效，上面全部重来
├─────────────────────────────────────┤
│ L3: RUN 下载依赖（少变）            │ ← 只在 pom.xml 变化时重建
├─────────────────────────────────────┤
│ L2: COPY pom.xml（很少变）          │
├─────────────────────────────────────┤
│ L1: 基础镜像 eclipse-temurin:25-jre │ ← 基础镜像引用未变化时通常可复用
└─────────────────────────────────────┘
```

- 这就是 **Docker 层缓存**：类比 npm 的 `package-lock.json` + CI 缓存——「不常变的放前面，常变的放后面」，顺序错了每次构建都全量重来。

> **生活版——叠乐高不用重搭**：一摞乐高从底座往上叠，你想换最上面一块，只需重插最上面几块；底座和中间没动的积木直接沿用，不用整摞推倒。换成容器：文件变更会产生可复用的差异层；当 `COPY` 的输入变化时，它及后续依赖它的构建步骤会失去缓存——所以「不常变的放下面（指令写前面），常变的放上面」，把 `COPY . .` 写在前面会让后续下载依赖的步骤频繁重跑。

```mermaid
flowchart TD
    L1["L1 基础镜像 eclipse-temurin:25-jre<br/>引用未变时通常可复用"] --> L2["L2 依赖清单 pom.xml（COPY 写在前面）<br/>很少变 → 只有改依赖才重建"]
    L2 --> L3["L3 下载的依赖<br/>最耗时 → 守在 pom 后面保住缓存"]
    L3 --> L4["L4 应用源码 app.jar<br/>常变 → 每次构建都重来"]
    L4 --> W["容器可写层<br/>运行时进程产生的文件写在这一层，镜像本身纹丝不动"]
```
- **Docker ≠ 容器本身**：Docker 是容器生态的「第一个普及者」，但镜像格式与运行时协议早已交给 **OCI（Open Container Initiative，开放容器倡议）** 标准化——K8s 集群里真正跑镜像的是 containerd / CRI-O 这类 OCI 实现，`docker build` 出来的镜像它们照跑不误。理解「镜像 = OCI 制品」，就理解了为什么 Docker 不是唯一的容器引擎。

> 官方依据：[Docker 存储驱动：镜像层与元数据](https://docs.docker.com/engine/storage/drivers/)；[Docker 构建缓存](https://docs.docker.com/build/cache/)。

### 3. Dockerfile 最佳实践

#### 3.1 多阶段构建（Java 服务的标准写法）

**多阶段构建**：一个 Dockerfile 里先在「构建阶段」用全量 JDK + Maven 编译，再把**产物**复制到「运行阶段」的轻量 JRE 镜像——编译工具链不进最终镜像。

先看单阶段里“文件变更形成差异层、配置指令写入镜像配置”的样子（多阶段只是先后搭两摞，最终只把第二摞留下）：

```mermaid
flowchart LR
    F["FROM 基础镜像<br/>提供已有文件系统层"] --> C1["COPY pom.xml<br/>新增文件系统差异层"]
    C1 --> C2["RUN mvn 下载依赖<br/>新增文件系统差异层"]
    C2 --> C3["ENV / USER / ENTRYPOINT 等<br/>更新镜像配置，不等于文件系统层"]
    C3 --> S["文件系统层 + 镜像配置 = 镜像<br/>运行时容器另有可写层"]
```

```dockerfile
# ========== 阶段一：构建（用完就丢，不进最终镜像） ==========
FROM maven:3.9-eclipse-temurin-25 AS builder
WORKDIR /build

# 为什么先只 COPY pom.xml？——依赖层只在 pom 变化时失效，
# 源码天天改也不会击穿「下载依赖」这个最耗时的缓存层（类比：先装依赖再 COPY 源码）
COPY pom.xml .
RUN mvn dependency:go-offline      # 预拉全部依赖到本地仓库

COPY src ./src
RUN mvn package -DskipTests        # 测试交给 CI 流水线，镜像构建保持快

# ========== 阶段二：运行（最终镜像只有这一段） ==========
FROM eclipse-temurin:25-jre           # 更小的 Alpine 变体以 Docker Hub 官方 tag 列表为准——别凭记忆猜 tag 名

# 安全基线：非 root 运行。root 容器被攻破 = 攻击者拿到 root 权限
# （Debian 系基础镜像用 groupadd/useradd；Alpine 镜像才是 addgroup -S / adduser -S）
RUN groupadd -r app && useradd -r -g app app
USER app

WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar

# 容器化 JVM 的内存预算：75% 只是本服务经压测后的起点，不是通用默认值。
# MaxRAMPercentage 控制 Java 堆占 JVM 可见内存的比例；还要给元空间、线程栈、直接内存等留余量。
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"

EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
```

#### 3.2 构建与缓存验证

```bash
# 构建时观察层缓存：第二次构建依赖层应显示 CACHED
docker build -t my-app:1.0 .

# 输出示例（注释即预期）：
# => [builder 2/6] WORKDIR /build                  0.0s  ← 命中缓存
# => CACHED [builder 3/6] COPY pom.xml .           0.0s  ← 命中缓存
# => CACHED [builder 4/6] RUN mvn dependency:go... 0.0s  ← 关键：依赖层没重建
# => [builder 5/6] COPY src ./src                  0.1s  ← 只有源码层重建

# 改一行代码再 build：只有 L5/L6 重跑，秒级完成
docker build -t my-app:1.1 .
```

#### 3.3 镜像瘦身三方案

| 方案 | 原理 | 坑 |
|-|-|-|
| Alpine 基础镜像 | musl libc 替代 glibc，体积小一半 | 个别依赖要求 glibc（Netty 原生库等）——选 `eclipse-temurin` 的 Alpine 变体而非自己拼 |
| **Distroless** | 只有运行时没有 shell / 包管理器 | 没法 `docker exec sh` 进容器排查，只保留必要调试手段 |
| **jlink 定制 JRE** | `jdeps` 分析后只打包用到的 JDK 模块 | 模块清单要维护；反射加载的模块 jdeps 看不见，要手补 |

```bash
# jlink：按需裁剪 JRE（先分析依赖，再打包）
jdeps --print-module-deps --ignore-missing-deps app.jar
# 输出示例：java.base,java.sql,java.naming,java.management  ← 用到的模块清单

jlink --add-modules java.base,java.sql,java.naming,java.management \
      --strip-debug --no-man-pages --no-header-files \
      --compress zip-6 \
      --output /custom-jre          # 产出一个 ~40MB 的定制 JRE（完整 JDK 300MB+）

# 然后在 Dockerfile 里 COPY --from=jre-builder /custom-jre /opt/jre
```

> **版本提醒**：新版 jlink 默认已裁剪调试信息等，参数以当前 JDK 的 jlink 手册为准——老博客参数别照抄。
>
> ⏸️ **短期可以不学**：jlink 是三种瘦身方案里性价比最低的——Alpine / Distroless 已能满足绝大多数场景，而模块清单要持续维护。**何时回来学**：镜像体积成为硬指标（冷启动计费、边缘设备、私有化交付）时。**面试最低要求**：能说出 jlink 是「用 jdeps 分析依赖、按需裁剪 JDK 模块」即可。

#### 3.4 安全基线清单

- 非 root 用户（见上面 Dockerfile）。
- **readOnlyRootFilesystem 只读根文件系统**：根文件系统挂只读，要写的路径显式挂 tmpfs / emptyDir——落盘型攻击与脏数据无处发生。
- **capabilities 最小化**：默认 capabilities 按 `drop: ["ALL"]` 全丢、再按需 `add` 个别能力——容器用不上的 root 权限一律不给。
- **`.dockerignore`**：构建上下文里不相关的文件不上传——类比 `.gitignore`，但它省的是「发给 daemon 的上下文体积 + 意外泄密」：

```text
# .dockerignore：密钥与本地环境绝不能进镜像层（进去了就永久留在层历史里！）
.env
.env.*
*.key
.git
.idea
target/
node_modules/
```

> **红线**：`.env` 被任何一层 `COPY` 过，即使下一层删除也**仍然可以从层里读出来**——密钥永远通过运行时环境变量 / Secret 注入，不进镜像。

### 4. 镜像仓库与漏洞扫描

- **私有仓库（Harbor）**：企业内部镜像托管；支持**多环境 promotion**——`dev → staging → prod` 推的是**同一个 digest**（镜像内容的哈希），保证「测过的就是上线的那一个」。

> ⏸️ **短期可以不学**：自建 Harbor 只在私有化 / 合规场景才需要——云厂商的容器镜像服务（ACR / ECR）开箱即用。**何时回来学**：公司要求内网自托管镜像、或你要做镜像仓库运维时。**面试最低要求**：能说出 tag 可覆盖、digest 不可变，生产按 digest 锁定。

> **生活版——网盘备份**：本地做好一份文件上传到网盘（push），换台电脑再从网盘拉下来（pull）继续用；文件改动了，传输时只传「新增差异」不是整份重传。换成容器：镜像推到 registry（Harbor / Docker Hub），运行环境按需拉取复用；**digest（镜像内容的指纹哈希）就像文件的指纹——内容一改指纹就变**，而 tag 只是「名字」，可以被人工覆盖指到别的版本。所以生产用 digest 锁定，保证「测过的就是上线的」。

```mermaid
sequenceDiagram
    participant D as 开发者
    participant B as docker build
    participant R as 镜像仓库 Registry（Harbor / Docker Hub / ECR）
    participant K as 运行环境（K8s 节点）
    D->>B: docker build -t my-app:1.0
    B->>B: 按 Dockerfile 逐层构建，未变的层直接复用缓存
    B->>R: docker push（增量只上传新增的差异层）
    K->>R: 部署时拉镜像 docker pull（生产按 digest 锁定）
    R-->>K: 返回镜像层
    K->>K: 拼层成文件系统视图，启动容器
    Note over B,R: digest=内容指纹，tag 可覆盖、digest 不可变
```

```bash
# digest（sha256:...）= 镜像内容的指纹；tag 可被覆盖，digest 不可变
docker push harbor.local/apps/my-app@sha256:abc123...
docker pull harbor.local/apps/my-app@sha256:abc123...   # 生产永远用 digest 锁定

# Trivy 扫描镜像层里的已知漏洞（CVE），CI 门禁用它拦截高危基础镜像
trivy image my-app:1.0 --severity HIGH,CRITICAL
# 输出示例（注释即预期）：
# eclipse-temurin:25-jre
# ====================================
# Total: 0 (HIGH: 0, CRITICAL: 0)   ← 干净，放行
```

### 5. Docker Compose 本地开发环境

- **Compose 是什么**：用一个 YAML 声明「本项目要哪几个容器怎么互联」——本地一键拉起 MySQL + Redis + Kafka，等价于前端项目里「一条命令起全套依赖」的 compose 模板。
- **只用于本地，不用于生产**：Compose 只能管「一台机器上的进程」，没有调度、自愈、水平扩缩——这正是下一讲 Kubernetes 来补的能力。

```yaml
# docker-compose.yml：与 .env 里的组件配置一一对应
services:
  mysql:
    image: mysql:8.4
    # 环境变量优先读根目录 .env（compose 的默认行为），实现「一处配置两处生效」
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: app_db
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql        # 命名卷：容器删了数据还在
    healthcheck:                          # 健康检查：真正能连上才算"就绪"
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10

  app:
    build: .
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/app_db
      # 关键：depends_on + condition=service_healthy
      # 没有这个，app 会在 MySQL 还在初始化时就连接（经典启动竞态）
    depends_on:
      mysql:
        condition: service_healthy
    ports:
      - "8080:8080"

volumes:
  mysql_data:
```

#### 5.1 容器网络与存储：四个高频边界

Compose 默认会为同一项目建立一个 bridge 网络，服务会以服务名注册到其中的 DNS。因此示例中的 `app` 应连接 `jdbc:mysql://mysql:3306/app_db`：`mysql` 是服务名，`3306` 是 **MySQL 容器内端口**。`localhost` 在容器内始终指向**当前这个容器自己**；只有在 MySQL 容器内执行 `mysqladmin -h localhost` 才是在访问 MySQL 本身。

| 场景 | 应写的地址/挂载 | 容易错成什么 | 原因 |
|-|-|-|-|
| `app` 容器访问 MySQL 容器 | `mysql:3306` | `localhost:3306` | `localhost` 不是另一个容器；服务名会随容器重建重新解析 |
| 宿主机浏览器访问应用 | `localhost:8080` | 用容器 IP | `ports: "8080:8080"` 才把宿主机端口发布到容器端口 |
| MySQL 持久化数据 | `mysql_data:/var/lib/mysql`（命名卷） | 写进容器可写层 | 命名卷由 Docker 管理，删容器后仍存在；`docker compose down -v` 才删它 |
| 本地开发时映射源码/配置 | `./config:/app/config:ro`（绑定挂载） | 当作可移植数据卷 | bind mount 直接依赖宿主机路径，并会遮住容器目标目录原有内容；只适合明确需要共享的开发文件 |

```yaml
services:
  app:
    # “宿主机 8080 -> app 容器 8080”；同网络的 mysql 不需要发布端口给 app。
    ports: ["8080:8080"]
    volumes:
      - ./config:/app/config:ro  # 开发配置示例；密钥仍应通过 Secret/受控环境注入
  mysql:
    volumes:
      - mysql_data:/var/lib/mysql
```

> 前端对照：开发服务器把 `localhost:5173` 暴露给浏览器，类似端口映射；但 Vite 代理到后端仍是一次网络转发，不能因此把容器内 `localhost` 当成“同 Compose 项目的服务名”。在 Compose 网络内优先用服务名，在宿主机才使用已发布的 host 端口。官方边界见 [Compose 网络与服务发现](https://docs.docker.com/compose/how-tos/networking/) 和 [Docker 存储类型](https://docs.docker.com/engine/storage/)。

上面的启动时序（重点看 healthcheck 怎么把「启动竞态」拦住）：

```mermaid
sequenceDiagram
    participant U as 开发者
    participant M as MySQL 容器
    participant A as app 容器
    U->>M: docker compose up 同时拉起
    Note over M: 开始初始化，端口还没就绪
    U->>A: mysql 依赖别的服务，先等它
    A->>M: 尝试 JDBC 连接
    M-->>A: Connection refused（还在初始化）
    Note over A: depends_on + condition=service_healthy<br/>卡住等待，不急着重试
    M-->>A: 健康检查通过，mysqladmin ping 通了
```

```bash
# 日常命令
docker compose up -d            # 后台拉起全部服务
docker compose ps               # 看状态（注意 health 列，starting≠healthy）
docker compose logs -f app      # 跟踪某个服务的日志
docker compose down             # 停止并删容器（命名卷保留）
docker compose down -v          # 连数据卷一起删（彻底重置本地环境）
```

> **生活版——盒子与盒子外贴的文件夹**：把资料放「盒子里」，盒子一扔资料就没了；把重要资料放进「盒子外面贴着的文件夹」，盒子换了、扔了，资料还在。换成容器：**命名卷（volume）是 Docker 托管的持久目录**，适合 MySQL 数据；**bind mount** 是把宿主机指定目录直接挂进去，适合本地源码或配置但路径耦合更强。`docker compose down` 不会删命名卷，只有 `down -v` 才连卷一起清空。

## 坑点提醒

- **层顺序错误 = 缓存全失效**：`COPY . .` 写在 `RUN mvn dependency:go-offline` 前面，每次改代码都重下依赖——把「少变的」放前面。
- **基础镜像用 `latest` tag**：某天 upstream 更新导致构建突变，且无法复现历史镜像——生产镜像**钉住具体版本或 digest**。
- **把 `.env` COPY 进镜像**：层历史里永久可提取，等于把密钥发布出去。
- **以 root 运行 + 没有内存预算**：容器被攻破会扩大权限面；即使现代 JDK 通常能识别 cgroup limit，若 Java 堆、元空间、线程栈、直接内存和文件页缓存等总量超过 limit，内核仍可能 OOM Kill。老旧或不兼容的 JDK/cgroup 组合也可能错误读取可用内存，必须在目标镜像实测。
- **Compose 只写启动顺序、不验证就绪**：应用可能在 MySQL 就绪前连接失败；用 healthcheck 表达依赖就绪，并让应用自身保留有界重试，避免把 Compose 配置当作运行期可用性保证。
- **在容器内把 `localhost` 当成同项目服务，或为内部调用滥发端口**：`localhost` 只指向当前容器；容器间用服务名和容器端口。端口映射是给宿主机/外部访问的边界，发布不必要的数据库端口会扩大暴露面。

## 常见面试题

### Q1：容器和虚拟机有什么区别？
**答**：
- **标准结论**：两者都做资源隔离，但隔离层级不同。虚拟机（VM）通过 Hypervisor 虚拟出完整硬件，每个 VM 里跑一个独立操作系统；容器不虚拟硬件，多个容器共享宿主机内核，靠命名空间隔离（Namespace）切视图、控制组（cgroup）限资源。
- **底层原理**：
  - **VM：强隔离、高开销**——隔离在 OS 之下，靠硬件虚拟化（KVM 等）实现，隔离最强但每个 VM 都要带一整套内核与系统库。
  - **容器：轻但隔离弱**——OS 级虚拟化，隔离在进程层面，启动就是启动一个进程（毫秒级 vs VM 秒级），密度高一个量级。代价是共享内核，内核漏洞可能穿透容器边界——这正是容器安全基线强调非 root 运行、drop capabilities 的原因。
- **工程实践**：业务服务用容器（无状态、要密度与启动速度）；数据库、强隔离或异构 OS 场景用 VM。生产里常见组合是「VM 里跑 K8s，K8s 里跑容器」，不是二选一。加分句：「容器快，是因为没有第二个内核要启动」。

### Q2：Docker 镜像为什么是分层的？怎么给镜像瘦身？
**答**：
- **标准结论**：镜像由若干只读的文件系统差异层和镜像配置组成；`RUN`、`COPY`、`ADD` 等文件变更会形成差异层，`LABEL` 等只改元数据。构建缓存与分发可复用这些结果。瘦身三板斧：多阶段构建、Alpine / Distroless 基础镜像、jlink 定制 JRE。
- **底层原理**：层（Layer）本质是文件系统差异集——靠 UnionFS（联合文件系统，就像把多张透明胶片叠在一起看，每层只记「自己那点的差异」）把多层拼成一个用户看到的视图，层间共享：不同镜像共用基础层，分发只传差异。`COPY` 输入变化会使其后依赖该结果的步骤失去缓存，所以「不常变的放前面、常变的放后面」。
- **工程实践**：先 COPY 依赖清单再 COPY 源码，依赖层不因改代码失效；生产钉版本不用 `latest`；`.dockerignore` 排除密钥与构建产物；最终镜像非 root 运行。误区：「删掉文件」不等于瘦身——被删内容仍留在底层里，瘦身必须从「不放进镜像」做起。

### Q3：多阶段构建解决了什么问题？为什么能显著减小镜像？
**答**：
- **标准结论**：一个 Dockerfile 里用多个 `FROM` 分阶段——构建阶段装全量 JDK + Maven 编译出 jar，运行阶段只把产物拷进轻量 JRE 镜像，最终镜像只含运行所需。
- **底层原理**：编译工具链（编译器、包管理器、源码、依赖缓存）动辄几百 MB，对运行毫无用处；多阶段构建用 `COPY --from=构建阶段` 在层层面只复制产物，把工具链留在可丢弃的构建镜像里。镜像小了：拉取快、启动快、攻击面小（工具链里常藏着可利用组件）。
- **工程实践**：Java 标准写法是 Maven 镜像构建 + Temurin JRE 运行；依赖层单独 `COPY pom.xml` 并 `RUN mvn dependency:go-offline` 保住缓存；测试交给 CI，镜像构建保持快。加分：把「构建时长（缓存）」与「镜像体积」两个优化维度分开讲。

### Q4：容器里的 JVM 为什么即使识别了容器内存也会 OOM？怎么做内存预算？
**答**：
- **标准结论**：当前受支持的 JDK 通常默认启用容器资源感知，会把 cgroup 内存限制作为 JVM 可见内存；这只解决“堆按什么基数计算”，不等于总内存安全。容器 limit 必须覆盖 Java 堆、元空间、代码缓存、线程栈、直接/本地内存和可能计入 cgroup 的页缓存。用 `-XX:MaxRAMPercentage` 或显式 `-Xmx` 设定堆预算，再用压测验证峰值与余量。
- **底层原理**：
  - **因果链**：Kubernetes/Docker 配置 memory limit → Linux cgroup 对该容器记账并施加限制 → JVM 的容器支持读取可用内存/CPU → `MaxRAMPercentage` 以该“JVM 可见内存”为基数计算最大 Java 堆；JVM 之外的内存不会自动挤进这个堆比例。
  - **75% 的由来**：它是常见的起始预算，不是 JDK 规则。余量要覆盖元空间、代码缓存、每个线程的栈、NIO/Netty 直接内存、JNI/GC 本地内存以及实际运行中的页面缓存；线程数、依赖和流量模型变了，比例也应重算。
- **工程实践**：
  - **版本差异**：不要把“JDK 10 起”误读为旧版一定按宿主机。较新的 JDK 8 更新版也引入了容器支持，但发行版、更新号与 cgroup v1/v2 组合不同；在目标镜像执行 `java -XshowSettings:system -version`，并确认 `UseContainerSupport` 未被关闭。
  - **配额联动**：例如 limit=1536Mi、堆暂定 75% 时，最大堆约为 1152Mi；其余约 384Mi 只是待压测验证的预算，不是保证。可按线程上限、直接内存上限和元空间监控结果把比例下调，或改用明确的 `-Xmx`。
  - **失败路径**：进程可能先抛出 `OutOfMemoryError`，也可能尚未堆满就因 cgroup 内存压力被内核杀死，Kubernetes 显示 `OOMKilled`。先看容器 limit、峰值 RSS、线程数、直接内存与重启原因，不要只盯 heap dump。
  - **加分**：CPU 也有对应问题——容器核数读错会影响 JVM 线程数与 ForkJoinPool 并行度。

> 官方依据：[Oracle `java` 命令参考：`MaxRAMPercentage`](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html)；[Oracle `UseContainerSupport`](https://docs.oracle.com/en/java/javase/17/docs/specs/man/java.html)；[Kubernetes：Pod 与容器资源管理](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)。

### Q5：Compose 中为什么容器间不能用 localhost？volume 和 bind mount 怎么选？
**答**：
- **标准结论**：容器内 `localhost` 是当前容器自己；同一 Compose 网络中的服务用服务名和容器端口通信，例如 `mysql:3306`。`ports: "3306:3306"` 是供宿主机访问的映射，不是 app 访问 MySQL 的前提。持久化数据库数据优先使用 Docker 管理的命名卷；本地需要直接共享源码或配置时再使用 bind mount。
- **底层原理**：Compose 为项目创建默认网络并提供服务名 DNS，容器 IP 重建后可能变化但服务名稳定。命名卷的存储位置由 Docker 管理；bind mount 直接映射宿主机路径，容器与宿主机可同时改同一文件，且会遮住目标目录原有内容。
- **工程实践**：只发布确实要被宿主机或外部访问的端口，数据库通常仅留在 Compose 内网；`mysql_data` 用于数据，`./config:/app/config:ro` 可用于开发配置。发生连不上时，先确认服务名、容器端口、网络归属和健康状态，再查端口映射，而不是先改成 `localhost`。
