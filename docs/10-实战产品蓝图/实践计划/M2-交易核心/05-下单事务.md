# M2-05：下单事务

返回 [实践计划与进度](../README.md)。

## 目标

登录用户能用 SKU 与数量列表创建订单，订单、明细、库存预扣在同一事务内原子完成。

## 范围

- t_order（id、order_no 唯一索引、user_id、status、total_amount、create_time、update_time）与 t_order_item（id、order_id、sku_id、quantity、price 下单时快照价）。
- 订单号生成器（雪花式实现，落 user-service，M3 再提升到 common-core）。
- POST /orders（请求体 items 列表；校验 SKU 与库存；价格取下单时快照；库存条件预扣 UPDATE locked = locked + n WHERE total - locked >= n，不足返回 409/40900；订单 + 明细 + 预扣同一 @Transactional）。

## 接口与事务约定

- 仅已登录用户可下单；用户 ID 从 JWT 主体取得。请求为 `{"items":[{"skuId":1,"quantity":2}]}`，明细 1–50 行、每行数量 1–999、SKU 不重复；客户端不提供价格、金额或订单状态。未认证为 `401/40100`，请求不合法为 `400/40000`。
- 商品上下文批量提供未删除且已上架 SKU 的当前报价；缺失或不可售 SKU 为 `404/40400`。订单上下文在创建时保存单价快照，用十进制金额计算总额，初始状态为 `CREATED`。响应返回订单 ID、订单号、状态与总额；明细读取留给 07 卡片。
- 库存上下文独占 `t_stock` 写入：订单服务的一个事务先写订单头与明细，再逐行执行数据库条件预扣；未配置或不足返回 `409/40900`，事务回滚订单、明细及此前已预扣的库存。并发预扣以数据库条件更新和检查约束为最终不变量。
- 订单号采用单实例雪花式毫秒时间戳 + worker ID + 毫秒内序列，数据库唯一索引最终兜底；本地默认 worker ID 为 0，多实例运行前必须为实例配置互不相同的 `BOOT_ORDER_WORKER_ID`。该机制不替代 06 卡片的请求幂等。

## 学习点

@Transactional 多表事务边界、快照价、条件更新预扣、订单号生成。

## 验收

1. 下单成功后订单、明细、库存 locked 三处变化一致，total_amount 等于快照价乘数量的合计。
2. 任一 SKU 库存不足时整单失败，无半截数据（订单/明细/库存均不落）。
3. `./mvnw -pl services/user-service -am test` 通过。

## 不做

- 不做幂等（06 卡片）。
- 不做购物车清空联动（前端组合）。
- 不做优惠券与地址（蓝图无此字段）。
