# M2-08：支付模拟

返回 [实践计划与进度](../README.md)。

## 目标

用户能对 CREATED 订单发起模拟支付，支付成功后订单转 PAID、预扣库存转实扣。

## 范围

- t_payment（id、order_id、pay_no、amount、status、create_time）；`order_id` 唯一，`pay_no` 仅作为外部可追踪的唯一支付流水号，不能充当同一订单支付幂等依据。
- POST /orders/{id}/pay 仅允许订单所有者操作。模拟渠道同步成功时，在同一事务中执行订单状态条件更新 `CREATED → PAID`、创建支付单，并将每个订单明细对应库存的 `total` 与 `locked` 同步减去数量。
- 订单状态条件更新必须使用 `UPDATE ... WHERE id = :id AND user_id = :userId AND status = 'CREATED'`；未命中后读取订单当前状态，`PAID` 或 `CANCELLED` 均返回 409/40900，不能创建支付单。
- 支付单 `status` 固定为 `SUCCESS`；本卡不建立 `PENDING`、失败重试或回调状态。支付金额必须等于订单的 `total_amount` 快照，不能重新按 SKU 当前价格计算。
- 支付时每条库存实扣都以 `locked >= :quantity` 为条件；任一更新未命中即抛出受控异常并回滚整个事务，不能留下「订单已支付但库存未实扣」或「支付单已创建但订单未支付」。
- `t_payment.order_id` 唯一索引是数据库最终不变量；订单状态条件更新是并发入口的第一道原子判断。两者共同保证一张订单至多一张成功支付单。

## 学习点

状态机条件更新（幂等三板斧第三斧）、支付幂等键、库存实扣。

## 验收

1. 支付后订单为 PAID，支付单为 SUCCESS 且金额等于订单快照总额，库存 total 与 locked 均精确扣减一次。
2. 并发支付同一 CREATED 订单时，只有一个请求成功；其余返回 409/40900，数据库恰有一张支付单，库存不重复扣减。
3. 对 PAID 或 CANCELLED 订单支付均返回 409/40900，且不产生新支付单。
4. 支付事务中任一库存实扣失败时，订单状态、支付单和所有库存更新全部回滚。
5. `mvnw.cmd -pl services/user-service -am test` 在 JDK 25 下通过。

## 不做

- 不接真实支付渠道。
- 不做退款。
- 不做异步回调（模拟同步成功）。

提交：本次提交（`feat: 新增订单模拟支付`）。

测试与接口证据：在 `boot-server/` 使用 Oracle JDK 25.0.4.1 执行 `./mvnw -q -pl services/user-service -am clean test`，26 份 Surefire 报告共 115 个测试，失败、错误、跳过均为 0；`git diff --check` 通过。

- 真实 HTTP：`POST /orders/{id}/pay` 仅允许订单所有者操作；支付金额取订单快照，SKU 后续改价不影响支付金额。支付成功后订单为 `PAID`、支付单为 `SUCCESS`，库存 `total` 与 `locked` 各精确扣减一次；未登录返回 `401/40100`，他人订单按不存在返回 `404/40400`。
- 并发与状态：同一 CREATED 订单并发支付恰有一个 `200`，另一个返回 `409/40900`，数据库只留一张支付单且库存只结算一次；对 PAID、CANCELLED 订单再次支付均返回冲突且不新增支付单。
- 原子回滚：双明细订单的第二条库存结算失败时，订单状态恢复为 `CREATED`、支付单不落库，第一条已执行的库存结算也完整回滚。订单状态更新同时包含订单 ID、当前用户与 `CREATED` 条件；库存实扣包含 `locked >= quantity` 条件。
- 分层与静态值审计：支付上下文通过订单与库存应用服务协作，不跨上下文直接写表，领域层不依赖框架；新增机器值只由 `PaymentStatus` 与既有 `OrderStatus` 持有，未新增部署配置、错误码、角色码或权限码。
